# ADR 0001：QMT 订单事实单调合并与恢复 latch

- 状态：Accepted
- 日期：2026-07-13

## 背景

XtQuant 的异步下单响应、委托回调、成交回调和主动查询不存在可依赖的到达顺序；官方接口还明确
说明宽松响应模式会使查询和推送时序不确定。同步撤单返回 0 只证明撤单指令已成功发出，不证明
订单已经撤销。若直接用最后到达的对象覆盖 OMS，会造成成交量倒退、`FILLED` 回退为活动状态、
撤单期间成交丢失，或快速重连绕过恢复对账。

## 决策

1. 订单事实按 broker identity 合并，`qmt_order_id` 与 `order_sysid` 均可关联同一 OMS 行；查询和成交
   关联同时限定 `account_id + execution_mode`。
2. `filled_quantity` 只增不减；`FILLED` 不被非 `FILLED` 覆盖，`CANCELLED/REJECTED` 不回退为普通
   活动状态。较旧查询与本地终态或成交量冲突时保留本地已确认事实、写审计并使本轮对账失败。
3. 成交回调可以在委托回调之前推进 `SUBMITTING → PARTIALLY_FILLED/FILLED`。后到的旧委托回调
   不能覆盖成交量、终态或策略发布 lineage。
4. 撤单指令成功发出后进入 `CANCELLING`。撤单期间的新成交增加成交量但保留撤单意图；全成后
   `FILLED` 胜出；撤单失败回到 `SUBMITTED` 或 `PARTIALLY_FILLED`。
5. 网关同时保存“历史内存订单”和“本轮查询订单 ID 集合”。活动订单一致性只使用本轮查询集合，
   不允许上一轮内存对象掩盖券商本轮缺失。
6. 断线和账户不健康设置 recovery latch。连接恢复本身不能清除 latch；只有账户健康、四类券商
   快照和 OMS 一致性全部成功后才清除。
7. 同一不一致事故的重复重试只写一次聚合审计；成功恢复后同一差异再次出现视为新事故。

## 结果

- 代价是短暂的券商旧快照可能触发 `HALTED`，需要新的可靠快照或操作员检查；这是交易安全上的
  有意保守选择。
- 内存、SQLite 与券商快照可以在异常瞬间显示差异，但系统不会把差异静默改写成一致。
- 自动测试覆盖成交先到、撤单竞争、撤单失败、快速重连、账户不健康、查询缺单、状态倒退和身份
  升级。真实活动订单断网/重启仍需在 qmt_sim 交易时段进行运行级验收。
